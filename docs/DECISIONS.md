# Архитектурные решения (ADRs)

Этот документ фиксирует ключевые архитектурные решения проекта LuminaBooks с обоснованием и рассмотренными альтернативами.

---

## 2026-06-28 — SQLite + better-sqlite3 как БД

- **Контекст:** Требовалось локальное хранилище данных для десктопного приложения. Данные: книги, коллекции, профиль, сессии чтения, история статусов.
- **Решение:** Выбрана SQLite через better-sqlite3 (синхронный API) с WAL-режимом.
- **Обоснование:**
  - Встраиваемая БД — не требует отдельного сервера
  - better-sqlite3 — самый быстрый SQLite-драйвер для Node.js (синхронный, нативный код)
  - WAL-режим обеспечивает конкурентное чтение без блокировок
  - Нулевая конфигурация для пользователя
  - Достаточная производительность для десктопного приложения с ~1000 книгами
- **Альтернативы:**
  - **PostgreSQL:** избыточен для десктопного приложения, требует установки сервера
  - **IndexedDB:** браузерный API, недоступен из Electron main process без лишних прослоек
  - **JSON-файлы:** нет ACID, нет индексов, сложнее миграции
  - **SQL.js (WebAssembly):** медленнее better-sqlite3, больше размер

## 2026-06-28 — JSON в TEXT-колонках вместо нормализации

- **Контекст:** Поля `sessions`, `statusHistory`, `franchiseIds` (в books) и `bookIds` (в franchises) хранят массивы данных. Нужно решить: нормализовать в отдельные таблицы или хранить как JSON.
- **Решение:** Хранить массивы как TEXT с JSON-сериализацией. При чтении парсить через `JSON.parse`, при записи — через `JSON.stringify`.
- **Обоснование:**
  - Сессии чтения и история статусов **всегда** запрашиваются вместе с книгой — отдельный JOIN был бы избыточен
  - JSON-поля не участвуют в поиске/фильтрации (фильтры идут по отдельным колонкам: status, rating, title, author)
  - Упрощает код — не нужно синхронизировать связанные таблицы
  - Избегает проблем N+1 при загрузке каталога
  - JSON-сериализация встроена в SQLite (json_extract), но не используется — парсинг на стороне приложения
- **Альтернативы:**
  - **Junction-таблица book_franchise:** усложняет CRUD, требует JOIN для отображения коллекций
  - **Отдельная таблица sessions:** потребовала бы JOIN или N+1 запросов при загрузке книг
  - **Отдельная таблица status_history:** та же проблема N+1

## 2026-06-28 — Pure React useState вместо Redux/Zustand

- **Контекст:** Нужно управлять состоянием приложения: книги, коллекции, профиль, настройки.
- **Решение:** Использовать только встроенные хуки React (useState, useEffect, useCallback, useRef) без внешних библиотек.
- **Обоснование:**
  - Приложение имеет ровно один экран (табы) — нет глубокой вложенности компонентов
  - Всего ~10 переменных состояния, все в App.tsx
  - Нет сложных действий с состоянием — только простые CRUD-операции
  - Отсутствие лишних зависимостей уменьшает размер бандла и упрощает поддержку
- **Альтернативы:**
  - **Redux:** избыточен для такого объёма состояния, много boilerplate
  - **Zustand:** проще Redux, но всё равно добавляет зависимость без существенной выгоды
  - **Jotai/Recoil:** атомарные состояния удобны, но не нужны при одном «источнике истины»

## 2026-06-28 — Три режима доступа к данным (IPC, HTTP, LocalStorage)

- **Контекст:** Приложение работает в трёх сценариях: (1) Electron с SQLite, (2) браузер с Express-сервером, (3) браузер без сервера.
- **Решение:** Реализовать единый интерфейс `ElectronDBAPI` с тремя реализациями, выбираемыми автоматически при загрузке.
- **Обоснование:**
  - Единый контракт позволяет остальному коду не знать о способе хранения
  - Автоматическое определение режима (через `window.electronAPI?.db` и `/api/status`) — zero-config для пользователя
  - LocalStorage-режим нужен для быстрого старта без установки
  - HTTP-режим обеспечивает синхронизацию между устройствами
- **Альтернативы:**
  - **Только Electron IPC:** потеря браузерного сценария
  - **Только HTTP API:** невозможность офлайн-работы без сервера
  - **Только LocalStorage:** нет синхронизации, ограничение 5MB

## 2026-06-28 — Express 5 для LAN-синхронизации

- **Контекст:** Нужно обеспечить синхронизацию данных между устройствами в локальной сети.
- **Решение:** Встроить Express 5 HTTP-сервер в Electron main process (порт 3456), предоставляющий REST API к той же БД SQLite.
- **Обоснование:**
  - HTTP REST — простейший протокол для интеграции, не требует дополнительных библиотек на клиенте (нативный fetch)
  - Express сервер делит код с IPC-обработчиками (один и тот же database.ts)
  - Легко отлаживать через curl/Postman
  - Порт 3456 не конфликтует с популярными сервисами
- **Альтернативы:**
  - **WebSockets (Socket.io):** избыточны для синхронизации по запросу (pull-модель)
  - **WebRTC:** сложен в настройке, требует STUN/TURN серверов
  - **gRPC:** тяжёлый, не вписывается в архитектуру Electron
  - **Облачный сервер:** противоречит концепции локального приложения

## 2026-06-28 — Electron + Vite

- **Контекст:** Нужна десктопная оболочка с современным инструментарием сборки.
- **Решение:** Electron 33 + Vite 6 + electron-builder.
- **Обоснование:**
  - Electron — зрелая платформа с доступом к файловой системе и SQLite
  - Vite — быстрая сборка в dev-режиме, плагин React SWC для JSX
  - electron-builder — мультиплатформенная упаковка (Windows/macOS/Linux)
  - Меньше порог входа для React-разработчиков
- **Альтернативы:**
  - **Tauri:** меньше потребление памяти, но Rust-бэкенд сложнее для быстрой разработки
  - **React Native Desktop:** менее зрелый, меньше сообщество
  - **NW.js:** менее популярен, хуже инструментарий
  - **Flutter Desktop:** Dart вместо TypeScript, другой стек технологий

## 2026-06-28 — Many-to-many через JSON-массивы

- **Контекст:** Связь между книгами и коллекциями — многие-ко-многим (книга может быть в нескольких коллекциях, коллекция содержит много книг).
- **Решение:** Хранить `franchiseIds` в таблице `books` (JSON-массив) и `bookIds` в таблице `franchises` (JSON-массив). Синхронизация — на стороне приложения.
- **Обоснование:**
  - Избегаем сложных SQL-запросов с JOIN
  - Все данные загружаются в память, связь вычисляется в JavaScript
  - Упрощает экспорт/импорт JSON
  - Для десктопного приложения с сотнями книг производительность приемлема
- **Альтернативы:**
  - **Junction-таблица book_franchise:** более «чистая» нормализация, но требует JOIN при каждом запросе
  - **Односторонняя связь (только в books):** неудобно показывать список книг коллекции без обратной связи

## 2026-06-28 — Клавиатурное управление таймером (Space / F)

- **Контекст:** В режиме чтения нужен таймер-секундомер. Пользователь должен быстро ставить на паузу и завершать сессию.
- **Решение:** Глобальные хоткеи: **Space** — пауза/продолжить, **F** — завершить сессию чтения.
- **Обоснование:**
  - Интуитивно понятно (Space — стандартный Play/Pause)
  - Минимизирует действия пользователя во время чтения
  - Реализовано через `useEffect` с `keydown` listener
- **Альтернативы:**
  - **Только UI-кнопки:** требует точного нажатия мышью
  - **Esc для паузы:** нестандартно

## 2026-06-28 — Google Books API интеграция

- **Контекст:** Пользователям нужен удобный способ заполнения информации о книге при добавлении.
- **Решение:** Интеграция с Google Books API через ключ API, вводимый пользователем в настройках. Результаты кешируются в локальной таблице `books_dictionary`.
- **Обоснование:**
  - Google Books — крупнейшая база книг с обложками, авторами, годами
  - API-ключ бесплатен (до определённого лимита)
  - Кеширование в словарь ускоряет повторный поиск и работает офлайн
  - Поиск по локальному словарю работает быстрее и не требует API-ключа
- **Альтернативы:**
  - **OpenLibrary API:** открытая БД, но менее полная
  - **Встроенный API-ключ:** небезопасно (ключ будет в коде)
  - **Только ручной ввод:** неудобно, требует точного копирования данных

## 2026-06-28 — Выбор Mantine UI v7

- **Контекст:** Необходим UI-кит с готовыми компонентами (модальные окна, поля ввода, дата-пикеры, селекты).
- **Решение:** Использовать Mantine UI v7.
- **Обоснование:**
  - Полный набор компонентов: модальные окна, формы, тултипы, уведомления, NumberInput, DateInput
  - Хорошая документация и TypeScript-поддержка
  - Совместимость с Tailwind CSS (не конфликтует)
  - Встроенный менеджер тем
- **Альтернативы:**
  - **Material UI:** тяжёлый, избыточный для десктоп-приложения
  - **Ant Design:** ориентирован на корпоративные дашборды
  - **Radix UI:** низкоуровневый, потребовал бы больше ручной работы
  - **Chakra UI:** менее популярен, меньше компонентов

## 2026-06-28 — Авто-определение статуса по датам

- **Контекст:** Пользователь может не указывать статус вручную — он должен определяться автоматически на основе заполненных дат.
- **Решение:** Реализована функция `updateBookStatusBasedOnDates`, которая запускается при каждой загрузке данных и определяет статус:
  - startDate + endDate → READ
  - startDate без endDate → READING
  - нет дат → WANT_TO_READ
  - ABANDONED/POSTPONED — не перезаписываются
- **Обоснование:**
  - Минимизирует ручные действия пользователя
  - Статус всегда синхронизирован с датами
  - Исключения (ABANDONED, POSTPONED) защищены от случайного перезаписывания
- **Альтернативы:**
  - **Только ручной выбор статуса:** путаница, когда даты не соответствуют статусу
  - **Запрет изменения статуса вручную:** ограничивает пользователя

## 2026-06-28 — Очередь уведомлений о достижениях

- **Контекст:** При разблокировке нескольких достижений одновременно (например, при импорте данных) они должны показываться по одному.
- **Решение:** Реализована очередь с отображением только первого элемента. Каждое уведомление показывается 6 секунд, затем автоматически скрывается и запускается следующее.
- **Обоснование:**
  - Предотвращает наложение уведомлений
  - Пользователь видит каждое достижение по отдельности
  - Авто-скрытие через 6 секунд с прогресс-баром
- **Альтернативы:**
  - **Одновременный показ всех:** наложение, невозможно прочитать
  - **Модальное окно:** прерывает работу
